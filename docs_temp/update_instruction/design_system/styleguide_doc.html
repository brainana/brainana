Brainana docs style guide

How the Read the Docs site at docs/*.rst should look and read. Brainana keeps the stock sphinx_rtd_theme and makes it quieter. Content changes happen in markup and wording. CSS stays a thin layer in docs/_static/custom.css. The light previews below show the target rendering inside the RTD theme.

1. Principles

  • Prose first. A sentence that reads well needs no decoration. Add structure such as a list, table or heading only when it helps the reader scan.
  • One signal per block. A paragraph may carry one emphasis device: one bold term, one admonition or one link-heavy line. Stacked signals cancel each other out.
  • Two brand colors, used generically. Purple and green, taken from the paper figures, are Brainana's visual identity. They carry no fixed meaning: purple is the primary accent (interface, links, first category), green is the secondary accent (second category, tips). What a color stands for in a given diagram is said by its caption or legend.
  • Color separates, it does not decorate. Use a hue only to tell two kinds of things apart or to mark the one interactive element. Everything else is grey.
  • One look across the site. All pages, mermaid diagrams, SVGs and embedded widgets draw from one palette: purple, green, slate and neutral grey, plus amber reserved for warnings. The RTD default blue and orange go away.
  • User-oriented. RTD tells users what to do and what they get. Evidence, internals and design rationale go in docs_temp/.

3. Diagrams and the palette

The reference is space_tracking.svg, generated by scripts/dev/docs/make_space_diagram.py. Its green/purple pair matches the paper figures (pipeline_overview.png, anat_workflow.png, …), and it becomes the brand palette for the whole site. Every new flowchart, mermaid block and hand-drawn SVG uses these values and no others.

Rules

  • A diagram uses at most three hues plus neutral, assigned in order: purple, then green, then slate. If one hue is enough (for example, to mark outputs), use purple and keep everything else neutral.
  • The caption or a legend says what each hue means in that diagram. The same hue may mean different things in different diagrams. Where a diagram contrasts anatomical and functional data, keeping the paper figures' pairing (anat green, func purple) is fine because it matches the figures, not because the colors are reserved.
  • No status colors (red/amber/green for pass/fail) in docs diagrams. Status belongs to the QC report palette.
  • No gradients, shadows, emoji or icons inside boxes. Bold/italic HTML inside mermaid labels is allowed for one title line per box.
  • Mermaid diagrams render at their natural size (labels at 13px, slightly smaller than body text) and only shrink on a narrow column. So prefer top→bottom (flowchart TB); a wide left→right chart with more than about 4 columns gets scaled down until its text is unreadable. custom.css resets the font of pre.mermaid to Lato, because the theme's monospace would otherwise overflow and clip labels. Spell words out in labels ("session", not "ses"). Keep labels at 3 lines or fewer and boxes at 12 or fewer. If you need more, split the diagram.
  • Generated SVGs record their generator in a comment, as make_space_diagram.py does. Edit the script, not the SVG.

Definition lists (term + indented body) give the scan-ability of bold lead-ins without the visual noise. RTD styles the term once, consistently. If items have 2 or more parallel attributes, use a list-table instead.

A real heading appears in the sidebar and the page TOC, gets an anchor and can be linked. A bold paragraph gets none of that. The same applies to italic sub-headings in outputs.rst. Use a rubric only for an unlinked label above a list, and never two in a row.

6. Admonitions

Allowed: note (purple), tip (green, sparingly), seealso (slate), warning (amber).
Do not use important, caution, attention, danger or custom admonition::.

  • At most one per section, and never back-to-back.
  • Never the first thing under a heading. Write the sentence first, then add the aside.
  • warning = data loss, wrong results or a run that will fail. A requirements list is not a warning.
  • No more than 3 lines. Longer than that means it is a section, as with synthesis_level.rst:169.
  • No bold or lists inside unless there is no other way.
Note
Replace <version> with a release tag.
Warning
Mounting the output folder read-only makes the run fail at the first write.
Tip
Run one subject first to check your paths before processing a whole dataset.
See also

7. Headings and page structure

LevelUnderlineUse
Page title=====One per page. Same wording as the toctree entry.
Section-----Main sections. These show in the sidebar.
Subsection~~~~~The usual depth limit.
Sub-subsection^^^^^Rare. Never skip a level (spaces_and_transforms.rst:161 jumps from - to ^).
  • Sentence case ("Create a configuration file", not "Creating A Configuration File"). Keep titles to about 60 characters or less. FAQ questions may be full questions, but cut the filler.
  • No hand-typed numbers ("2.1 Bias field correction"). They drift. If order matters, the page order already shows it.
  • Underline length = title length. Sphinx accepts longer ones, but they make the source noisy to read.
  • No manual tables of contents. The RTD sidebar and .. contents:: :local: do this (see faq.rst:10–27).
  • No ---- transitions between sections. A heading already separates them.
  • Pages over about 400 source lines should be considered for a split. The lines in a raw widget don't count.
  • Toctree captions use the theme's own style. Do not type them in ALL CAPS in source.

8. Figures and tables

Don't (index.rst)
.. image:: _static/.../pipeline_overview.png
   :alt: Brainana pipeline overview schematic
   :align: center
   :width: 100%

|
Do
.. figure:: _static/.../pipeline_overview.png
   :alt: Anatomical and functional pipelines
         converge in T1w and template space.
   :width: 100%

   Pipeline overview. Green: anatomical;
   purple: functional.  (caption states the
   meaning of each hue)
  • Always use figure with :alt: (what it shows) and a one-line caption. When the figure is color-coded, the caption names the colors.
  • Width: 100% for schematics, max 720px for SVG diagrams, and screenshots at natural size up to 100%. Let CSS handle spacing; never add | spacers.
  • Prefer SVG for diagrams. Paper PNGs stay as they are, but put new diagrams in the §3 palette.
  • Tables: list-table with :header-rows: 1 and :widths:. Use them when items share two or more attributes. Cells hold short phrases, not paragraphs. If a column repeats the same value in every row, drop it (processing.rst:501, "Domain").
  • Long filename inventories (outputs.rst) are better as a tree block plus a short "what each file is" table than as many code-only bullets.

9. Code blocks

ContentDirective
Commands the user runs.. code-block:: bash. Use console only when the block shows output too.
Config.. code-block:: yaml
Directory layouts.. code-block:: tree. This is the project's lexer; never a bare :: (usage_notes.rst:46).
CLI synopsis, log text.. code-block:: text
Windows.. code-block:: powershell
  • Never use a bare :: literal block. Always name the language.
  • Syntax colors come from the palette only, and nothing is bold. Code is ink #404040. Comments are muted italic #6b6b6b. Keywords, shell builtins and YAML keys are --bn-purple-dark. Strings and numbers are --bn-green-dark. Everything else, including the \ line continuation, stays ink. This replaces Pygments' default (bold green builtins, bold brown \, teal comments, red strings) through overrides in custom.css; pygments_style is left unset.
  • Keep blocks copy-pasteable: no $ prompts in bash blocks, and placeholders written as <version>, explained once in the sentence before the block.
  • Don't repeat a long command on two pages. Link to the canonical one (the docker run appears twice in usage_notes).

11. Interactive pages

Two interactive surfaces live in the docs: the configuration generator (_static/config_generator.html, a standalone page) and the transform-command builder (raw:: html inside spaces_and_transforms.rst).

  • Widgets embedded inside an RTD page follow this guide: neutral greys (#f6f7f8 panels, #d6d9dc borders), purple for interactive accents, and the §4 code surface for code output. No dark code panel (the builder's #1e1e2e/#cdd6f4), no GitHub grey (#f6f8fa/#d0d7de) and no amber hint box (#fff8e1/#f9a825). Hints use the §6 note style.
  • The standalone configuration generator follows this guide too: the dark sidebar with the cream logo header and a "← Brainana docs" link, Lato bold section titles (unlike the docs' Roboto Slab) with the config key as a chip; every direct child of a section is a white card (a plain option, or a pipeline module with its checkbox and its advanced settings opening inside the card); each option inside a card is a settings row (name and help on the left, control in a fixed right column, hairline between rows); subgroups are small muted key labels; purple controls, a cream --bn-surface Generate button (dark text, #e6e1cd border, purple border on hover), amber validation errors, green success notes, and YAML output in the code surface. Its stylesheet is a single <style> block built from the §2 tokens.
  • Inline <style> in a widget is scoped under one wrapper class, so it can't leak into the theme.

12. Feature and choice cards

Today the generator appears only as a bullet ("Use the interactive configuration generator…") in usage_notes.rst, plus passing links in the FAQ and atlas zoo. It is one of the most useful things in the docs: 70+ options grouped by stage, advanced toggles, a YAML download, and a test (test_config_consistency.py) that checks every key in defaults.yaml has a field. Choice cards

When a page offers two parallel paths, such as Docker vs Brainana Lite on installation.rst, show them as two side-by-side cards rather than a bold list. Each card has a title, a one-line pitch, a muted "Best for …" line and one bold arrow link to that path. The first or recommended option gets a --bn-purple top rule and, optionally, a :bn-tag:`Recommended` pill. The second option gets a --bn-green-mid rule. Use at most two or three cards, and only on landing or choice pages.

13. Review checklist

Before merging a docs change:

  • No bold lead-ins, bold pseudo-headings or italic pseudo-headings.
  • Bold appears only where a term is defined; UI labels use :guilabel:.
  • At most one admonition per section, none directly under a heading, and warning only for real failure risks.
  • Heading levels follow = - ~ ^ without skipping. Sentence case, no numbers, underlines match.
  • Every image is a figure with :alt: and a caption, and there are no | spacers.
  • Every code block names its language, and commands are copy-pasteable.
  • Diagrams use only the §3 palette; grep shows no stray hex values outside it.
  • Terms match §10 (FastSurfer, BOLD, skull stripping, US spelling).
  • Links to the configuration generator go to :doc:`config_generator`.
  • Local build (docs/build_rtd_local.sh, .rtd-venv) shows no new warnings.
